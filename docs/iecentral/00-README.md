# IECentral — System Documentation

IECentral is the internal business platform for **Import-Export Tire (IET)**, a tire
distributor. It is a single Next.js application that has grown into a broad ERP/HR/operations
suite — roughly 40 functional modules spanning HR & payroll, recruiting, reporting on
distribution data, internal communications, and warehouse/field operations — backed by a
Convex realtime database and a set of AWS Lambda services for the heavy/long-running work.

This folder is the entry point. Each cluster has its own deep-dive document; this README gives
the architecture at a glance, a module map, the shared infrastructure (S3 buckets, AWS stacks),
and the cross-cutting findings the documentation pass surfaced.

> **Looking for the end-user (non-technical) guide?** See [`../user-guide/`](../user-guide/00-README.md)
> — plain-language, task-oriented help for employees, organized to mirror the six clusters below.

## Architecture at a glance

| Layer | Technology | Notes |
|---|---|---|
| Frontend | **Next.js 15 (App Router)**, React 19, Tailwind v4 | PWA via `next-pwa`. Client components throughout (`"use client"`). |
| Hosting | **Vercel** | `iecentral.com` / `www.iecentral.com` builds from `origin/main`. |
| Backend / DB | **Convex** (`outstanding-dalmatian-787`) | Queries/mutations/actions in `convex/*.ts`; ~149 tables in `convex/schema.ts`. Realtime subscriptions. |
| Heavy compute | **AWS Lambda** (3 SAM stacks) | Dunlop/OEIVAL processing, scanner MDM, Office→PDF. |
| Object storage | **AWS S3** (5 buckets) | Report files, inventory caches, documents, training video, safety photos. |
| AI | **Anthropic SDK** (`@anthropic-ai/sdk`) | Résumé matching, AI interview, project tasks, meeting notes, tech wizard. |

**Deploy model:** pushing to `origin/main` triggers the Vercel build, and `vercel.json`'s build
command also pushes the Convex deployment — so **a single `git push` deploys both frontend and
backend**. Code that depends on a Convex schema/function change ships together with the UI that
uses it.

### Repository layout

```
app/            Next.js routes (one folder per module) + app/api/* route handlers
components/     Shared + per-module React components (dochub/, email/, meetings/, shell/, …)
convex/         Backend: schema.ts + one file per domain + convex/email/* + _generated/
lib/            Browser/server helpers (permissions, brand mapping, tire search, webrtc, …)
aws/            SAM stacks: dunlop-reporter/, scanner-mdm/, office-to-pdf/, email-proxy/
docs/           This documentation + superpowers/ plans & specs
scripts/        One-off + maintenance scripts
```

### The OEIVAL two-cache design (load-bearing — read before touching inventory)

Tire-label lookup and inventory **reporting** read different caches in `ietires-dunlop-jmk-uploads`,
both built by the `dunlop-oeival-processor` Lambda on every OEIVAL upload:

- `_cache/latest.*` — **reporting snapshot**: the *latest upload only*, overwritten each time. Read
  by the `inventory-data` / `custom-data` report routes so reports always reflect the newest file.
- `_cache/lookup.*` — **collective tire-label index**: a cumulative union by `itemId` that
  *never shrinks*. Read by `lib/oeivalBrandIndex.ts` (`resolveBrand` / `searchTires`). This exists
  so a partial upload (e.g. `IET-oeival R20 ONLY.csv`) can refresh reports **without** wiping out
  tire-label coverage for every other tire.

Always **stream the NDJSON.gz** cache line-by-line; never `XLSX.read` the raw OEIVAL workbook in a
Vercel function — it OOM-kills the 2048 MB serverless function.

## Cross-cutting findings (flagged during documentation)

These came out of reading the code and are recorded here so they aren't lost. **They are
observations, not changes** — verify and prioritize before acting.

- **RBAC is largely unenforced on the backend.** Verified in a full backend read — see
  [SECURITY-FINDINGS.md](SECURITY-FINDINGS.md): ~195 guard call-sites across 21 of ~90 files, so
  most of the 665 mutations have no permission check and many trust a client-supplied `userId`.
  The original audits' headline example (`auth.updateUser` self-promotion) is now **fixed/stale**.
  The worst anonymous secret-disclosure / privilege-escalation paths have now been **closed**
  (`seedSuperuser`, the QBWC/Zoom credential queries, the Doc Hub folder-password bypass); a
  prioritized CRITICAL/HIGH backlog remains in SECURITY-FINDINGS.md. **Highest-priority area.**
- **`convex/deletedRecords.ts`** is the only file using Convex's built-in `ctx.auth.getUserIdentity()`,
  which `authGuards.ts` says is not wired up — so soft-delete/restore may throw for everyone via the
  normal client path. Worth verifying. ([01](01-platform-architecture.md))
- **Name/table collisions** that mislead: `convex/documentSignatures.ts` is the **Doc Hub** backend
  (not the onboarding `documentSignatures` table); `convex/emails.ts` is transactional Resend mail
  (not the email *client*, which is `convex/email/*`); `convex/aiTasks.ts` is **project** task
  generation (not recruiting). ([03](03-recruiting-reviews-training.md), [05](05-communications.md))
- **Possible web-push delivery bug:** push subscriptions may bind to the `next-pwa` Workbox service
  worker, which has no `push` handler — pushes may never display. ([05](05-communications.md))
- **Orphans / dead wiring:** `employeePushTokens` table (native push actually uses
  `users.expoPushToken`), `emailRetryQueue`, `pushNotifications.sendClockOutReminders` (no cron),
  a half-built meeting lobby, calendar `notifiedAt` set but no notification wiring.
  ([05](05-communications.md))
- **`convex/activity.ts` has no backing table** — the activity feed is synthesized per call and
  scales poorly. ([06](06-operations-field.md))
- **Plaintext secrets in a few spots:** location security codes, computer admin/user passwords,
  the QBWC `wcPassword`. ([02](02-hr-time-payroll.md), [06](06-operations-field.md))
- **Scheduling/automation gaps:** WTD daily-run and dealer-rebates have no dedicated cron (they fan
  out from `/api/reports/process`); there are two coexisting ingestion paths and two Dunlop
  monthly-run implementations (one unscheduled). ([04](04-reports-data-platform.md))

## Conventions

- **Backend access pattern:** UI calls Convex via `useQuery`/`useMutation` (`convex/react`); API
  route handlers in `app/api/*` cover the things Convex can't (S3 presigning, Lambda invocation,
  IMAP/SMTP, PDF/Office processing, SOAP for QBWC, third-party webhooks).
- **Auth in handlers:** most functions take a `requestingUserId` argument rather than deriving the
  caller from a session — central to the RBAC findings above.
- **Long/heavy work** (200 MB report parsing, Office conversion, scanner provisioning, IMAP egress)
  is pushed to AWS Lambda, not done in Vercel functions.
- **Printing:** prefer **jsPDF**-built documents (tire labels, safety reports) over browser
  `@media print` for anything that must be exactly one page.
